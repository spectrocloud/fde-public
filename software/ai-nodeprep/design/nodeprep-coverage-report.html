  • 0.1.36 — cold cycle verdict, and a misdiagnosis corrected. The awaited cold power cycle changed the failure instead of fixing it: with PF_NUM_OF_VF_VALID=True in NV the firmware programs no SR-IOV PCIe capability at all (lspci capability list without SR-IOV, no sriov_totalvfs in sysfs), on both CX-4 Lx cards. The second cold cycle pending at publication was overtaken by events: the operator removed the node for a fresh reinstall (cold boots included) and dropped the profile to eastWest.numVFs=1 for a base-scenario test first.
  • 0.1.37 — reconcile-path audit: the re-walk logic is correct; one reboot gap closed. Asked to verify whether a VF-count change reverts to the earlier steps: it does. A profile generation bump re-opens every step and rewinds to Provisioning (agent §5.1 reset), so grubParams re-derives its IOMMU want-list from the new numVFs and mlxconfig re-queries every device and re-flashes on any NV drift (up or down) before requesting its apply reboot — exactly the chain that ran live in the gen-11 walk. The audit found one real gap instead: the grub step wrote its drop-in but never requested the reboot that applies it (the GrubChanged reboot reason existed but had no call site) — a grub-only change would have sat unapplied until an unrelated reboot. 0.1.37 raises it: a written drop-in now requests the reboot, and the §5.2 hold serializes it with the mlxconfig apply reboot.
  • 0.1.38 — inventory vs. MFT install order, graceful. The fresh-node walk of bl-r1-c2-02 exposed a live-noise defect: enrichMellanox ran mlxconfig q per function every cycle before aptPackages had installed MFT, logging four "not classified (mlxconfig unavailable: exit status 127)" lines per poll cycle through the whole Provisioning window. No correctness harm — rail assignment is sysfs/profile-only, the failed classifications are retried every refresh, classification lands the cycle after MFT appears (refreshInventory precedes runStage), and the Configuring mlxconfig step gates on the tool anyway — but the wording read as errors. 0.1.38 detects the missing tool once per pass (findHostTool), skips the per-device exec attempts, and logs a single per-process notice ("MFT not installed yet; N function(s) pending classification — the aptPackages step installs it"); unclassified functions keep reporting Type=Mellanox in the status until classified. A mlxconfig that IS installed but fails per device still logs per device.
  • 0.1.39 — checkpoint reboot protocol (bash needs_reboot semantics). The fresh-node walk of bl-r1-c2-02 then failed: grubParams' 0.1.37 reboot request armed its 60s timer at request time while aptPackages was still configuring doca-all; the grace expired mid-dpkg, the node rebooted with packages half-configured, and every apt retry then died on E: dpkg was interrupted until the retry budget failed the NodePrep. The bash never races like this — it accumulates needs_reboot across a block and reboots after the block finishes. 0.1.39 adopts that: requestRebootBg now RECORDS requests (deduped, event per new reason) and checkpointReboot fires one aggregated reboot only when a stage pass makes no progress — so doca-install + grub + ib_core requests share a single boot (the grouping the operator described), the timer never races a running install, and a walk that converges without needing the fresh boot (firmware ceiling already sufficient) reaches Ready with the NV change pending for the next natural reboot instead of rebooting unconditionally (a deliberate improvement over the bash's always-reboot-after-config, v105 L939). Also: aptPackages now raises the long-planned DocaInstalled reboot reason (v105 L353) — coalesced by the checkpoint — and runs dpkg --configure -a before installing, healing the interrupted state the old bug created (live-verified on the resumed walk).
  • 0.1.40 — reboot gate taxonomy (operator-directed) and boot-transient re-verify. The checkpoint reboot worked end-to-end on bl-r1-c2-02 (reboot #1 carried doca+grub+ib_core; reboot #2 carried the mlxconfig apply), but exposed the follow-on defect: the mlxconfig reboot rode into Finalizing and wiped OS-level state after those steps had gone Done — sriovNumVFs read Done "0→1" against a host showing numvfs=0 (the driver re-probe resets the count), the per-VF sriov/ sysfs dirs had vanished with it, and vfGuids parked Blocked forever because Done steps never re-run. 0.1.40 re-opens the runtime-transient steps (sriovNumVFs, vfGuids, disableACS — setpci's ACS clears are equally boot-transient) at every boot change, matching the bash's complete-stage semantics where the OS-level state is established after the last reboot. The reboot-gate taxonomy also landed: profile firmware.version (new field — the target version inside the configured BFB, e.g. 32.49.1014) gates BlueField-3 flashing — running version equal → Done, no flash, no reboot; mismatch → Blocked naming the delta until the v0.2 flash apply (which then reboots), and the gate needs MFT's flint classification to have landed before it judges. ConnectX-class adapters are never version-compared (their firmware comes from the DOCA install). Ordering is structural: the BFB flash step (Flashing) precedes the mlxconfig config step (Configuring), so a config apply always happens after a pending firmware upgrade — the new image resets NV to its defaults. CRD note: firmware.version must also land in the external manifest system (see the CRD-trap note in §2) or the field is pruned on write.
  • 0.1.41 — VF GUID/MAC write semantics (live-established, three experiments on CX-4 Lx FW 14.32.1010). The first full VF-identity apply on the fresh node failed with "GUID readback mismatch after rebind": the write-while-bound order (bash fn_set_vfs L655-800) is wiped by the rebind — at bind the firmware re-derives the node GUID (EUI-64 from the VF MAC) whenever the vf entry carries no staged value. The bash never noticed: it only logs the readback, never verifies, so on this firmware class its own end state is defaulted GUIDs. The Go verify is deliberately stricter, so 0.1.41 adopts the ordering the experiments proved: unbind → write → bind, with every bounced VF getting its FULL identity set (node always; port/policy for IB; mac for ETH legacy) staged inside the unbound window. Two subtleties the experiments surfaced: writing mac resets a previously staged node GUID (the firmware regenerates it from the new MAC asynchronously — node written immediately after is clobbered, so node is written last with a ≥2s gap after the mac write), and the mac sysfs attr is write-only (reads return a usage string), so drift detection and verification now go through the VF netdev's address. Verified end-to-end through the agent on a deliberately seeded node-GUID drift; one late firmware re-derive (~90s after a bounce) was observed once and self-healed at the next boot-verify pass — boot-verify is the safety net for this firmware's flakiness.
  • 0.1.42 — virtual functions are first-class in the device model. With VFs existing on the host, boot-verify's mlxconfig pass failed forever on them (mlxconfig q on a VF exits 3 — VFs have no device NV of their own), and worse: vfCountFor returned eastWest.numVFs for a VF's rail label, so a re-walk would have written sriov_numvfs on a VF. 0.1.42 adds an isVF flag to the inventory device model (kernel-canonical physfn test) and gates every consumer: mlxconfig skips VFs (config is inherited from the PF), vfCountFor returns 0 (VFs do not get VFs), and railFns excludes them (netplan/udev/lossless targets are PF-only — VF naming and GUIDs are driven through the PF by vfGuids). Ops note from the same investigation: a same-tag redeploy with imagePullPolicy: IfNotPresent is a no-op — the node keeps the first build it pulled under that tag; one version per build is now hard discipline.
  • 0.1.43 — ACS-disable yields to SR-IOV VFs (operator-directed). VFs and disabling ACS are mutually exclusive; a profile can express both, so the resolution is in the step: when eastWest.numVFs > 0 or northSouth.numVFs > 0, disableACS is ignored (Done-skip with an explanatory message), however it is set. Detection-only effect on the gen-13 walk: that walk ran the old logic and had already cleared ACS on 5 devices with numVFs=1 — ACS is runtime-only, so the next reboot restores hardware default and the skipping step then leaves it alone; the step never re-enables ACS itself.
  • 0.1.44 — reference-cluster comparison: VF MTU and link state (operator-corrected −50 bug). Kevin deployed a bash-reference cluster (4 VFs east-west, bl-r1-c2-05) for a direct comparison. Two discrepancies fixed, both from fn_rename_devices' VF block: the VF netdevs' MTU and link state were never converged by the controller (1500/down vs the reference's up), and the bash's VF MTU formula subtracts 50 bytes unconditionally — a switchdev headroom the reference applied in legacy mode too (8950). 0.1.44 puts VF MTU + bring-up in udevRules (the fn_rename_devices counterpart) with the corrected formula: legacy → full profile MTU (our node: 9000), switchdev → −50; representors get the −50 treatment best-effort under switchdev. VF MTU/link is ip link runtime state wiped at boot, so udevRules joined the boot-transient re-open list and Ready-phase boot-verify re-applies it — the controller's equivalent of the bash's rc.local re-running the whole precomplete block at every boot. Deliberate divergences the same comparison confirmed (kept): (1) VF node GUIDs — the reference shows EUI-64 defaults because the bash writes while bound and only logs the readback (§2, 0.1.41); the controller synthesizes and verifies the real GUIDs (90:5a:08:1f:…), the bash's intent. (2) The reference created 4 VFs on the non-rail bond0 LOM card (bash applies NUMVF_EW to every ConnectX function); the controller deliberately leaves non-rail-mapped functions alone (operator correction, 2026-09-03). (3) The reference ran ACS-disable with VFs present — the exact bug 0.1.43 fixed.

§4What v0.1 adds beyond the bash script

The rewrite was an opportunity to fix what the script could not do, and every item below was exercised in this run.

  • CAPI pause/unpause of the Machine — the node is owned exclusively during prep (MachinePaused/MachineUnpaused events, annotation verified on the Machine, released on Ready and on de-adoption). The bash script had no notion of CAPI at all.
  • sha256-verified downloads with .tmp+rename — a truncated or MITM'd BFB cannot be flashed.
  • Firmware cache reuse — a local spcx copy that still hashes to the profile's checksum is reused instead of re-fetched, so re-preps move zero bytes over the wire (proven live: 1.5 GB reused); without a configured checksum nothing is trusted and the fetch always runs.
  • Declared, inspectable state — the 15-step ledger, phase, reboot count and per-step messages are a kubectl object, not a file inside a container image.
  • Crash-safe resume — a Failed NodePrep recovers by annotation without re-imaging (used live after the aptPackages bug).
  • Per-step criticality — a failed critical step (SR-IOV, udev, lossless RoCE, OVS, ACS) blocks Ready and holds the taint; non-critical failures do not poison the node.
  • Boot verification protocol — boot-ID change detection, reboot counting, taint held until the new boot is verified, all evented.
  • Host-mutation guardrails — detect-only mode (no -host-mutations) turns every mutating step into a Blocked report instead of an error.
  • OOM-safe heavy exec — apt/dpkg run in transient host systemd units, not as pod children; the agent pod cannot be OOM-killed by host package management (the 0.1.7 fix, shipped before this run).
  • Render-time syntax gate — the boot hook is parsed by the host's own /bin/sh before it can replace a working file (the 0.1.10 fix from reboot #1).
  • Auditability — every host command, download and transition is logged with duration and bounded output, and surfaced as Kubernetes events.
  • Selection modes — adoption no longer requires the ai-worker label: selection.mode is labelSelector (legacy behavior, still the default), allWorkers, or allNodes (control planes included, and only together with policy.controlPlanePrep); selection.excludeLabel disqualifies nodes under every mode. All proven live in Run 3.
  • Control-plane quorum window — at most expected−quorum CP members mid-prep at once (1 of 3, 2 of 5), serialized further by strategy, admitted via the MaintenanceAdmitted condition, re-checked fail-closed inside the agent; Machines pause on adoption and unpause at Ready. Proven on the 3-node CP: one at a time, and one reboot mid-prep with etcd quorum 2/3 held.
  • Profile-edit re-walk — bumping the profile generation re-opens every step and rewinds the NodePrep to Provisioning, so a changed profile can't hide behind stale "Done" steps.

§5Honest gaps — what is not converted yet

Ordered roughly by when they would bite. Runs 2 and 3 closed the ConnectX-path gaps (mlxconfig, netplan, udev renames, 0-VF SR-IOV, ACS, ib_core netns) and the every-node gaps apt upgrade and NFSoRDMA; what remains needs hardware or modes the lab doesn't have.

Needing hardware or modes beyond the lab

  • BFB flash apply — the BlueField-3 gate, rshim discovery and BFB config plumbing are in and gate-proven, but bfb-install itself needs a BlueField-3, which the lab cluster doesn't carry (v0.2).
  • VF pipeline end-to-end — closed for the base scenario (2026-09-04, 0.1.41/0.1.42): after the fresh reinstall and the 0.1.36 NV revert, numVFs=1 walked end-to-end on bl-r1-c2-02 — NV config, sriov_numvfs, VF GUID/MAC synthesis and apply (the unbound-window semantics, §2), udev rename rules — to Ready with BootVerified and the taint released. Still open: higher VF counts on this hardware (only 1 VF exercised), the switchdev branch (devlink eswitch flip, OVS bridges, representor rename rules), and the InfiniBand link-type path (port GUID + policy) — each needs the corresponding hardware/mode.
  • OVS switchdev convergence — br-rail-* bridge membership (libovsdb) is v0.2; the lab runs eswitch legacy (the step's gate verified).
  • True lossless-RoCE application — the step's body (mlnx_qos/mlnxreg, Spectrum-X CC daemon) is implemented but only runs on SuperNIC/ConnectX-7..9 per the bash gate; the lab's CX-4 Lx correctly skips it, so a real application run needs that hardware class.
  • SR-IOV device-plugin pod bounce after VF creation, so the plugin re-discovers VFs. (The rshim service enable/restart itself landed in 0.1.30 as rshimService — what remains here is rshim discovery as part of a real BlueField flash.)
  • [pending] VF GUID/MAC ownership under the NVIDIA Network Operator — verify the moment the operator is installed on the test cluster. It may implement its own VF GUID/MAC assignment (already observed in the switchdev path); nodeprep's vfGuids drift-repairs identity on every boot-verify pass, so two owners would fight — drift → re-taint → repair → rewrite → endless loop. If the operator does rewrite identity, vfGuids must stand down (or scope its repair), and sriovNumVFs/udevRules need the same ownership check.
  • 0.1.45 — cordonDuringVFConfig removed (operator decision). The knob was never implemented — and discussion of it established why it is redundant: the nodeprep taint (default-on, taintEnabled) already holds the node unschedulable through the entire walk including VF config, is derived state re-applied on every reconcile (self-healing, unlike the bash's imperative cordon/uncordon pair which strands a cordoned node on mid-run failure), and covers the taintEnabled: false case differently by design (that operator asked to be schedulable). Field dropped from the Go struct, the CRD (live + manifests), and the design-doc example profile. External-manifest note: the CRD copy in Kevin's management system must drop cordonDuringVFConfig too (alongside firmware.version from 0.1.40) or its reverts will out-vote the working tree.
  • 0.1.46 — hostBoot.iommu: auto live-verified (closes an "implemented but untested" item from the 0.1.45 status review). Profile gen 14 set iommu: auto; the derivation took the CPU-vendor branch (/proc/cpuinfo → vendor_id: GenuineIntel → intel_iommu=on) plus the VF-driven iommu=pt, matched the running kernel and the existing 90-nodeprep.cfg (unchanged file), so the step reported Done with no grub write, no reboot (reboots stayed 4), and the taint cycled once around the no-op re-walk. Remaining untested variants: amd/off (need AMD hardware / an iommu-off profile), hugepages params, and grubCPUVendor's AMD/unknown branches (unit-untestable — reads /proc/cpuinfo directly; the Intel path is what this run exercised).

On every node

§6Defects the live loop caught (and the fixes shipped)

Each of these passed the unit-test suite and failed only on real hardware — the reason the live-cluster mandate paid for itself.

Agent pod OOMKilled during DOCA install (0.1.7, first live pass). apt-get install doca-all as a pod child counted its memory against the pod limit. Fix: heavyHostExec runs package management in transient host systemd units via systemd-run — host-accounted memory, fail-fast on concurrent retries, idempotent re-runs. Live-proven across this run's installs.

Missing install subcommand (0.1.8, this run's fresh node). apt-get --yes doca-all → "E: Invalid operation doca-all", exit 100, 5 attempts exhausted, NodePrep Failed. Its gate tests asserted decisions, not command shape. Fix in 0.1.9; the run then completed to Ready in ~1 minute via the resume path.

Stray quote in the rendered boot hook (0.1.9, reboot #1). One bad character made dash reject the whole script at boot; the kubelet manager-state reset silently never ran and the node crashlooped — the exact failure class the hook exists to prevent. Fix in 0.1.10: candidate script is validated by the host's own /bin/sh (sh -n via nsenter) before it can replace a working file, plus a test parsing all 21 rendering variants with real sh -n. Reboot #2 then proved the repaired hook end-to-end with planted corruption.

Boot hook installed too late for the first prep reboot (0.1.14, Run 2). The hook (kubelet manager-state reset + mlnx wait) was only installed during the Finalizing kubeletState step, but the first nodeprep reboot happens in Provisioning (ib_core reload) — so both workers crashlooped kubelet on stale memory_manager_state the moment they came back. Fix: the agent installs the hook in every cycle, before any stage that can request a reboot. Proven by Run 2's second reboot: hook ran pre-kubelet, journal clean, no crashloop.

losslessRoce overreached the bash gate and misread its own readback (0.1.15, Run 2). The first body applied PFC/ECN to every rail NIC when the bash gates the entire fn_set_lossless_roce body on SuperNIC/ConnectX-7..9 — on CX-4 Lx the ecn sysfs interface doesn't exist at all, so the step Failed 5 attempts and parked the NodePrep. The PFC verify also matched the comma-separated --pfc input form against mlnx_qos output, which prints a column table. Fix: whole-body class gate restored (off-class hardware skips honestly, naming its inventory), column-table parser, unit tests for both.

Ready-phase boot-verify re-ran every step body every poll cycle (0.1.16/0.1.17, Run 2). On a Ready node the agent's 5-second cycle re-ran the full critical-step bodies for drift detection: ~40 mlxconfig per-key queries plus an ACS setpci sweep over every BDF — hundreds of host commands, forever. Fix, two parts: Ready-phase verification is throttled (immediately on a boot change, otherwise at most every 5 minutes, matching the design's "drift or a new boot re-verifies"), and the mlxconfig detect went from one query per key to one full query per device (the boot hook's corrective systemctl work is likewise once per process, not per cycle). Steady state on a Ready node is now zero host execs between verify passes, and the ACS read sweep runs quiet — devices without the capability are an expected per-device negative, counted in the step message instead of logged (0.1.18). A 0.1.22 follow-up: the lspci -d *:*:* enumeration still dumped its full ~466-line listing every verify pass (the sweep's last action, reading like a device dump); it and the per-device setpci writes now run quiet too, and the step message itself is the mutation record — "disabled ACS on: <devices> (N already clear, M without ACS capability)" — logged on change by boot-verify as well, so a drift repair is visible in logs and status alike. The remaining tool dumps followed (0.1.23): mlxconfig/flint device queries and mlnx_qos readbacks also run quiet, all behind a troubleshooting toggle — -verbose or NODEPREP_VERBOSE=true (kubectl set env) — that restores every exec and dump in full (verified both ways: 15-line startup log compact, ~1700 lines verbose, back to 15). A Ready node's steady-state log is now mode line, classification lines, and boot-hook install — nothing else between verify passes.

NodePrepProfile updates impossible: stale resourceVersion replayed from last-applied-configuration (Run 2, user-reported). Client-side apply embeds the manifest in the annotation on first apply; an export from another cluster carries its old resourceVersion into that annotation, and every subsequent apply replays it as an optimistic-concurrency guard → "the object has been modified". Fix: one-time kubectl annotate nodeprepprofile <name> kubectl.kubernetes.io/last-applied-configuration-, keep exports free of server-side metadata (or apply with --server-side). Root-caused live, documented in the controller README.

The initramfs ate the modprobe.d write — ib_core rebooted forever (0.1.25, Run 3). The ib_core netns step writes /etc/modprobe.d/ib_core.conf and reboots to reload the module, but ib_core.ko can ship inside the initramfs — whose copy of /etc/modprobe.d is baked when the package set is installed. With aptUpgrade in the same stage that bake happened four seconds before the write; the module loaded from the initramfs with the compiled-in default, every reboot came back unchanged, and the loop burned seven reboots. Fix: update-initramfs -u after the write, before the reboot request. The next run rebooted exactly once and verified netns_mode=0 matches profile — with the conf confirmed inside the refreshed initramfs.

Profile edits never re-opened Done steps (0.1.26, Run 3). The design's profile-generation check existed but observedProfileGeneration was only written at adoption and the per-step hash was dead code — flipping aptUpgrade/nfsRdma on a converged fleet changed nothing. Fix: the agent's cycle compares profile.Generation against the status on every pass; a bump resets every step to Pending and rewinds to Provisioning, and the steps re-verify idempotently (each of Run 3's profile bumps re-walked the fleet this way). Per-step input hashing lands with real Apply.

The quorum window deadlocked on its own queue (0.1.27, Run 3). The §6.4 busy-counter counted every non-Ready control-plane NodePrep — including peers parked at MaintenanceAdmitted=False (QuorumFloor) — so with three CPs each member saw "2 other control-plane node(s) mid-prep" and none could ever be admitted. Fix: BusyControlPlane — waiting is not busy; a peer consumes the window only once admitted or past Provisioning. Verified live: strict cp13 → cp15 → cp14 serialization, one member mid-prep at a time.

The agent failed open on missing admission — and its reboots clobbered conditions (0.1.28, Run 3). Two defects on the same gate. (1) A queued CP whose MaintenanceAdmitted condition had not arrived yet fell through the agent's check as if consented and could walk Provisioning outside the window (pool-16 prepped un-admitted this way). Fix: the agent fails closed for control planes — a missing condition is not consent — with the node's role cached for a minute. (2) requestReboot patched the whole conditions array from a stale copy every cycle, deleting the controller-written conditions, including the admission itself. Fix: single-condition patches via fresh read-modify-write.

The cluster's NodePrepProfile CRD was reverted to the pre-selection schema (Run 3, operational). The CRDs on this cluster are enforced by an external management system that reverts any drift to its own copy — so the pre-selection schema came back on its own, spec.selection became an unknown field and was silently pruned on every write, and the whole fleet de-adopted with "no longer matches any profile". Remediation was a stopgap: re-apply the working-tree CRD and re-add selection with kubectl patch --type=json — JSON patches do not touch last-applied-configuration, so prefer them over apply for live profile edits. The durable rule: CRD and RBAC manifest changes must land in the external management system first; applying them directly to the cluster is temporary by construction.

Apt saw the literal $(uname -r) (0.1.30, Run 3 audit round). The profile lists linux-headers-$(uname -r) — the bash expands it because the bash is a shell. The agent execs argv arrays through nsenter with no shell, so apt received the literal text and failed exit 100; the gen-10 profile bump re-opened every step and the whole fleet exhausted its retry budget on aptPackages within minutes. Fix: the agent expands the one supported placeholder from the host's uname -r before detect or install, refuses any other shell expression instead of passing it to apt, and apt-mark holds freshly installed linux-headers-* (bash L325). Host-verified: hold ok installed for the running kernel's headers.

The walk didn't wait for its own reboot (0.1.31). mlxconfig applied the NUM_OF_VFS drift and requested the apply reboot; the 60-second reboot grace then ran out while runStage kept stepping — the phase advanced to Finalizing and kubeletState restarted kubelet on a host that was seconds from going down. Fix: the cycle holds the walk while RebootRequired=True (whenever -allow-reboot is set) — the boot_id change clears the condition and re-verification resumes the walk, which is the bash config→reboot→precomplete sequence made explicit. A failed reboot command now also emits RebootFailed, so a parked NodePrep is never silent.

The firmware ignored NUM_OF_VFS until PF_NUM_OF_VF_VALID (0.1.32). After the apply reboot the firmware NV carried NUM_OF_VFS=4 — and the PCIe SR-IOV capability still reported TotalVFs: 1. The device (Supermicro LOM, FW 14.32.1010, PSID SM_1211000001000) ships PF_NUM_OF_VF_VALID=False, which makes the firmware disregard NUM_OF_VFS entirely. The bash script never sets the flag — on its production firmware the default evidently differs. Fix: the flash set now carries PF_NUM_OF_VF_VALID=1 next to SRIOV_EN (query-gated, so firmware that doesn't expose the key skips it), and sriovNumVFs' ceiling message names the flag when it reads False.

Warm reboots do not reload SR-IOV NV settings (0.1.34). With NUM_OF_VFS=4 and PF_NUM_OF_VF_VALID=True in NV, two full warm reboots left TotalVFs: 1 on all four functions — mlxconfig's "please power cycle machine" is literal for this firmware class: the PCIe SR-IOV capability is programmed at device power-on, so only a cold (AC) cycle loads it. The bash script never hits this because it runs inside provisioning, where the fleet tooling cold-cycles the machine right after firmware configuration. Two smaller findings from the same window: vfGuids burned its five attempts on "no IB device" while the PF was re-probing across those reboots — transient states now Block instead of Failed (0.1.33) — and the resume annotation only re-opens Failed steps, so the mid-upgrade residue (mlxconfig already Done before the flag fix) needed a one-time manual NV set on the remaining three functions, the exact command sequence the agent runs. sriovNumVFs now consults the firmware NV in its Blocked message: it distinguishes "NV not yet written (the mlxconfig apply reboot will land it)" from "NV written but not loaded (cold power cycle needed)" — and the live ledger currently says exactly that, with the node parked honestly until the cold cycle.

Test-harness hygiene: MachineHealthCheck maxUnhealthy was patched to 0% before the reboot tests (all runs) so its 10-minute Ready-timeout could not deprovision the Machine mid-test, and was restored to 100% after each verification completed. The first (unpatched) reboot attempt did get remediated — the cluster deleted the Machine and MAAS re-racked it, which is itself what provided the fresh-node test bed. One Run 3 infrastructure incident, not a controller defect: vm-cp-pool-16 hung mid-prep (kernel up, sshd and kubelet dead for hours) with the nodeprep pause annotation on its Machine, which blocked CAPI remediation; unpausing and deleting the Machine let the machine controller replace it (vm-cp-pool-14), which joined and prepped cleanly. Worth a hypervisor look if it recurs — pool-13 survived the identical sequence.
