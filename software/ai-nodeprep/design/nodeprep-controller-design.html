01

The incumbent

What nodeprep-v105.sh actually does, and where its architecture stops scaling — ten specific pains, each of which the controller design answers in a later part.

The script runs at every boot on each AI-capable Kubernetes node. It sources /opt/spectrocloud/nodeprep.env, guarantees its own re-execution via an /etc/rc.local entry (unless Palette's stylus-agent owns the node), then walks a five-state machine persisted as the spectrocloud.com/nodeprep label on its Node object:

  1. init — install prerequisites: download BFB and DOCA repo deb from the MAAS TFTP server, apt upgrade, kernel headers (held), gcc-12, doca-all + MFT + lldpd; write GRUB cmdline (IOMMU per CPU vendor, iommu=pt, hugepages), ib_core netns_mode=0, lldpd config; enable rshim; reboot.
  2. inithw — hardware inventory via mst/mlxconfig/flint, published as spectrocloud.com/nic-N-* and gpu-N-* labels; flash BlueField-3 SuperNICs (and DPUs, policy permitting) with bfb-install over rshim in parallel, version-gated by vercomp; reboot.
  3. config — mlxconfig reset + set per device class: link types (east-west / north-south), SR-IOV enable, VF counts, RoCE CNP DSCP 48, adaptive routing & congestion-control keys for Spectrum-X, INTERNAL_CPU_OFFLOAD_ENGINE for DPUs; per-rail netplan files; reboot.
  4. precomplete — disable ACS on PCIe switches (optional), create VFs on sysfs, synthesize and write VF node/port GUIDs and MACs (unbind/rebind to activate), write udev rename rules (eth_rN, roce_rN, nic_vfN_*, VF representors), trigger udev, configure lossless RoCE (PFC 3, DSCP trust, ECN, ROCE_ACCL, doca_spcx_cc, IPG), reset OVS with DOCA options and build br-rail-rN DPDK bridges, add PFs to bridges, restart the SRIOV device plugin, uncordon, remove the nodeprep taint on control planes.
  5. complete — and because precomplete falls through to complete in the same case branch, every subsequent boot re-runs the entire finalization sequence as a crude converge mechanism.

1.2Where it hurts

These are numbered — the design refers back to them as P1…P10.

02

Design principles

Eight commitments that shape everything downstream.

  1. The CRD is the state machine; the agent is stateless hands. All progress lives in NodePrep.status. The agent pod can die, be rescheduled, or be rebooted at any instant — the next reconcile resumes from what was persisted, never from memory.
  2. Every mutation is a step with Detect → Apply → Verify. A step reads the host, reports clean/drifted, applies idempotently, then re-reads to prove the end state. There is no "run this script" step anywhere.
  3. Reboots are first-class objects of the protocol, not shutdown calls sprinkled through code: requested in status, executed once, detected via boot_id, counted, and budgeted.
  4. Policy and mechanics are separated. The cluster controller owns taints, cordons, fleet flash windows and profile propagation; the node agent owns every touch of hardware, packages and boot config.
  5. No action without a profile. Nodes are adopted explicitly via NodePrepProfile.nodeSelector. An unmanaged AI node is visible (no NodePrep object), not silently mutated by accident.
  6. Status over labels. Structured inventory lives in status.nics[]/status.gpus[]. The spectrocloud.com/nic-N-* labels survive as an opt-in compatibility generator so existing dashboards keep working.
  7. Failure is a first-class phase. Bounded retries with backoff end in Failed with the exact step, attempt count and stderr — not an exit code in a log file.
  8. Observable by default: structured logs, Kubernetes Events on the NodePrep object, and Prometheus metrics for step results, reboots, and flash durations.
  9. The taint is a held maintenance window, not a one-shot flag. It persists across reboots in etcd, is released only by boot-time verification, and is re-applied whenever disruptive work must run — one mechanism covering bring-up, post-reboot recovery, and maintenance (§6.1).
Key insight — the reboot trick dissolves

The bash script's central hack — rc.local self-re-execution so the state machine survives reboots — is exactly what a DaemonSet already is. The agent pod starts on every node boot, reads its NodePrep object, compares boot_id, and continues. Nothing is installed into the boot path of the OS at all.

API design

Two cluster-scoped kinds. The profile is the declarative form of every nodeprep.env variable; the NodePrep object is the per-node state machine and inventory.

3.1NodePrepProfile

One profile can serve a whole rack class; nodeSelector decides which nodes adopt it. Field names follow the domain (rail, east-west, north-south), not the env-var spellings.

3.3Why status, not labels

Labels were the bash script's only channel, so everything became one: state, inventory, firmware versions. The controller keeps exactly one label — the compat generator's output — and moves the rest into a typed, watchable, diffable resource. Concrete wins:

  • kubectl get nodeprep -o wide replaces parsing eight labels per NIC;
  • status writes go through the status subresource — agents can never clobber spec, and controller/agent writes don't collide (agent owns inventory + step progress, controller owns phase gating + conditions like flash admission);
  • firmware history lives in Events when it changes, so a silent regression is visible.

With policy.labelCompat: v1, the controller regenerates the legacy spectrocloud.com/nic-N-{type,fw,psid,addr,name,linkwidth,linkspeed,rail} labels from status.nics[] in deterministic order — same values the bash script produced, so existing tooling is unaffected during migration.

Architecture

Two binaries, one Go module: a cluster controller (Deployment) and a node agent (privileged DaemonSet). All communication flows through the API server.

4.2The agent runtime

  • Pod shape: privileged, hostPID: true, hostNetwork: false, mounts /host (chroot root), /sys rw, /dev (rshim, mst), /run/udev. Tolerates the nodeprep taint and control-plane taints — the agent must run on a tainted node, or nothing could ever remove the taint.
  • Host tooling via chroot: the agent image contains only Go binaries and a minimal runtime; every host operation is chroot /host … against tools installed on the host itself (mft, mlxconfig, devlink, iproute2). This keeps version coupling honest: the tools match the host kernel the DOCA stack was installed for.
  • Package operations take flock on /host/var/lib/dpkg/lock to avoid racing host unattended-upgrades.
  • Node identity comes from the NODE_NAME downward API — no hostname -f guessing (fixes P9).
  • Single writer: the agent holds a coordination.k8s.io Lease per node before mutating anything; adoption of a previously bash-prepped node removes the rc.local entry under the same lease.
  • Boot hook: the agent renders and maintains nodeprep-boot.service (§6.2) — the only OS boot integration, versioned in Go, replacing rc.local.

Reconciliation model

A stage DAG of idempotent steps, a persisted step ledger, and a reboot protocol that survives power loss at any point.

5.1The step abstraction

// A Step is one idempotent host mutation with a verifiable end state.
type Step interface {
    Name() string
    // Hash of every input that determines the end state (profile fields,
    // inventory, package versions). A changed hash re-opens a Done step.
    InputsHash(ctx context.Context, inv *Inventory) (string, error)
    // Inspect the host: Clean | Drifted | Done.
    Detect(ctx context.Context, inv *Inventory) (State, error)
    // Move the host toward the end state. Must be safe to interrupt;
    // reports coarse progress for status.steps updates.
    Apply(ctx context.Context, inv *Inventory, report Progress) error
    // Prove the end state by re-reading the host, independent of Apply.
    Verify(ctx context.Context, inv *Inventory) error
    // True if Apply can disturb running workloads (VF rebind, eswitch
    // mode change, kubelet restart) — gates cordon + maintenance policy.
    Disruptive() bool
}

Example — the VF GUID step's Detect, which reproduces the bash script's read-compare-repair loop as a pure predicate:

func (s *VFGuids) Detect(ctx context.Context, inv *Inventory) (State, error) {
    for _, nic := range inv.VFProviders(s.profile) {  // SuperNIC/CX: eastWest, DPU: northSouth
        want := s.profile.VFCountFor(nic)
        if got, err := s.mlx.SRIOVNumVFs(nic.PCI); err != nil || got != want {
            return Drifted, err
        }
        for vf := 0; vf < want; vf++ {
            node, port, mac := GUIDScheme.For(nic, vf)   // §8.3 — byte-identical to v105
            if !s.mlx.VFGuidsMatch(nic.IBDev, vf, node, port, mac) {
                return Drifted, nil
            }
        }
    }
    return Done, nil
}

5.2Stages and the reboot protocol

Stages exist only where the hardware demands sequencing: you cannot mlxconfig a card that is being flashed, and link-type changes need a reboot to take effect. Within a boot, stages run back-to-back; a stage that ends clean hands straight to the next — the fast path when a node is already converged.

The reboot protocol, end to end:

  1. A step's Apply sets RebootRequired with a reason (doca installed, BFB flashed, mlxconfig applied, grub changed).
  2. At stage end the agent persists phase = nextStage before acting on the condition — a crash here means the reboot happens without progress being lost, the safe order.
  3. Controller cordons the node if policy says so; agent executes nsenter -t 1 systemctl reboot after a 60s grace period (preserving today's shutdown -r +1 margin for status writes).
  4. Node boots. The boot hook has already repaired connectivity (wait out mlnx_interface_mgr, re-apply netplan) and reset kubelet manager state per policy — before kubelet starts (§6.2). Kubelet comes up; the DaemonSet pod starts. This, not rc.local, is the boot trigger.
  5. Agent reads /proc/sys/kernel/random/boot_id, sees a change, clears RebootRequired, increments reboots.perStage, resumes the persisted phase. It then runs boot-verify: Detect over the runtime-critical steps — and because the taint persisted in etcd, no workload has been able to schedule since kubelet re-registered the node. Only when boot-verify is clean does the agent release the taint (§6.1). Completion is simply the first boot that passes this gate.
  6. A stage exceeding 3 reboots (or a step exceeding its apply-retry budget with exponential backoff, 30s → 16m) moves the NodePrep to Failed with the offending step, attempt count and output — and an Event. Recovery is explicit: bump the profile generation or annotate nodeprep.spectrocloud.com/resume.

5.3Convergence and drift

  • During bring-up (any phase before Ready) the agent re-runs Detect for every step on start and after each reboot — the persisted step ledger with inputsHash makes this cheap, only drifted or re-opened steps apply.
  • In Ready, a detect-only pass runs every 10 minutes and on agent start, and drift is classified. Non-disruptive drift (udev rule files deleted, netplan drop-ins edited, driver-ready marker missing, OVS options wiped — repairable with file writes, ensure-transactions and sysfs setters) is repaired immediately. Disruptive drift (VF rebind, eswitch mode flip, conf.db reset, interface renames, kubelet restart) is not: it re-enters the taint contract (§6.1) — the controller re-applies the taint, turning the node into a maintenance window, the agent converges inside it, and the taint releases again after verification. A repair that needs a reboot follows §5.2. Stricter than the bash script, which re-ran the whole finalization on every boot whether or not pods were running — and more thorough than detect-only, which left drift unrepaired until maintenance.
  • Kubelet CPU/memory manager state is cleared by the boot hook (§6.2) using the guarded sequence — stop kubelet if running, delete, restart — because deleting the files under a live kubelet races its re-persist of in-memory manager state and the stale file survives. In the normal boot path the hook runs Before=kubelet.service, kubelet is not yet up, and this reduces to a plain rm. When the agent must reset kubelet state outside the boot path (adopting a live bash-era node, post-boot repair), the same sequence runs as a disruptive step under the taint window — stopping kubelet does not kill the agent pod, since containers are managed by the still-running runtime, so the agent completes stop→delete→start and waits for the kubelet to re-register. always (default, bash parity) | readyCheck (skip the deletion when NodePrep is Ready, preserving CPU pin assignments across ordinary reboots; opt-in pending validation) | off.
  • Profile changes bump observedProfileGeneration; steps whose inputsHash changed re-open automatically. Changing eastWest.numVFs from 8 to 16 re-runs exactly the mlxconfig, numvfs, GUID and device-plugin steps — nothing else.
06

The taint contract, boot hooks & control plane

The cluster-level behaviors that today live in three places — the bash script's taint dance, the hand-edited rc.local, and the legacy nodeprep-controller — unified into one design.

6.1The taint contract: a held maintenance window, not a one-shot flag

Today the taint is removed once, at completion fixes P11. Everything after that is on trust: a node that reboots weeks later comes up Ready and untainted, and the scheduler can place customer workloads before the runtime settings — VFs, lossless RoCE parameters, ACS, OVS bridges — have been reapplied. The design inverts the lifecycle:

  • The taint is never "removed at completion" — it is released after verification, at every boot. Taints live on the Node object in etcd, so the taint survives a reboot for free: it is already present before kubelet re-registers the node. There is no scheduling race window at all — not a small one, none. (Kubelet manages only its own not-ready/unreachable taints and never touches foreign ones.)
  • Boot-verify is the release gate. On every boot the agent runs Detect over the runtime-critical steps — VF counts, VF GUIDs, udev rules and the resulting interface names, lossless RoCE parameters, OVS bridges, ACS state, driver-ready marker. Sysfs/devlink/file reads; seconds, not minutes. While the taint is held, no customer workload can be scheduled — which makes this also the one moment where disruptive repair is free.
  • Clean → release. The agent removes the taint, the controller restores the worker-role label, NodePrep is Ready. Drift found → repair under the held taint, reboot if required (the taint persists through the reboot), loop. The first boot that passes this gate is the completion event; every later boot passes the same gate. Completion and post-reboot recovery are one mechanism, not two.
  • Disruptive drift on a live Ready node re-enters the same state: the controller re-applies the taint, the node becomes a maintenance window again, the agent converges inside it, the taint releases after verification (§5.3). One mechanism for bring-up, post-reboot recovery, and maintenance.
  • Agent failure fails safe. If the agent cannot run (image pull failure, API unreachable), the taint stays — the node is unusable but never silently unverified. On an AI fabric that is the correct trade: customer workloads on a node with broken RoCE VFs are worse than a node that waits. Monitoring surfaces the stuck-taint state.
Why no drain is needed

nodeprep-initiated reboots always happen under the held taint, so nothing can be scheduled onto the node across them; running AI jobs die with the reboot regardless of drain semantics, and checkpointing is the workload's own concern. Post-completion reboots are covered by the boot-verify gate above. PodDisruptionBudget-aware draining would add failure modes (stuck drains on AI DaemonSet jobs) without protecting anything the taint doesn't already protect. Cordon-only stands — now with an explicit rationale instead of inertia. The cost of the contract: non-tolerating pods start a minute or so later after each reboot, and DaemonSets that must run early (CNI, CSI) already carry broad tolerations.

6.2Boot hooks: the two fixes that must run before Kubernetes

Two of the bash script's jobs genuinely cannot move into a pod, for the same chicken-and-egg reason in both cases: a pod needs a healthy kubelet and working connectivity, and these fixes exist to provide exactly that fixes P12.

  • Kubelet CPU/memory manager state. Stale cpu_manager_state/memory_manager_state files can keep the kubelet from starting after a reboot — and a dead kubelet can never schedule the DaemonSet pod that would clean them up. The deletion must remain a pre-kubelet action, as it is in the bash script today.
  • mlnx_interface_mgr VLAN-IP wipe. The mft interface manager has a bug that wipes active IPs on VLAN subinterfaces; on a node whose only addressing rides on VLAN subinterfaces, that cuts the node off from the API server entirely. Waiting out the manager and re-applying netplan afterwards is therefore a pre-connectivity repair: an agent-based repair would need the very network it is supposed to be fixing — even the agent image pull would fail. One bash detail is load-bearing and carries over: the manager service (and its transient system-mlnx_interface_mgr.slice) only exists when Mellanox hardware is present, so the wait is gated on both the manager script being installed and a 15b3 device being enumerated — the bash script's [ -f /usr/bin/mlnx_interface_mgr.sh ] && [ $(lspci -d 15b3:* | wc -l) -gt 0 ]. Without that gate, a node whose BlueFields are absent or failed pays the full 600s timeout at every single boot.

The design does not deny the need for a boot-time script — it removes the reasons rc.local was bad: invisible to the cluster, unversioned, unmanaged. The agent renders a small systemd oneshot from a template versioned in the Go source:

# /etc/systemd/system/nodeprep-boot.service — rendered by the agent, content-hashed
[Unit]
Description=nodeprep pre-kubelet boot hook (managed — do not edit)
Before=kubelet.service
# no After=mlnx_interface_mgr.service: it is a transient unit that may not exist
# (hardware-dependent); the hook polls for it behind a hardware gate instead

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/nodeprep-boot-hook

[Install]
WantedBy=multi-user.target

#!/bin/sh — nodeprep-boot-hook, rendered alongside the unit; failures logged to the journal
# The manager only exists when its hardware does — wait only when BOTH hold,
# else the wait can never succeed and every boot burns the full timeout.
if [ -f /usr/bin/mlnx_interface_mgr.sh ] && grep -qs 0x15b3 /sys/bus/pci/devices/*/vendor; then
  wait_for_mlnx_interface_mgr --timeout 600s   # as fn_ensure_nodeprep does today; sysfs ≡ lspci -d 15b3:*
  netplan apply                                # restore VLAN subinterface IPs the manager wiped
fi
case "$KUBELET_STATE_RESET" in
  always)     reset_kubelet_state ;;
  readyCheck) probe NodePrep phase via kubelet.conf (short timeout) — skip when Ready,
                reset_kubelet_state on any error (fail-safe = bash parity) ;;
esac

reset_kubelet_state() {
  # never delete under a running kubelet: it holds manager state in memory and
  # re-persists it (checkpoint / shutdown), so rm-while-running races that write
  # and the stale file survives — stop, delete, restart, as L112–115 does
  if systemctl is-active --quiet kubelet; then
    systemctl stop kubelet
    rm -f /var/lib/kubelet/cpu_manager_state /var/lib/kubelet/memory_manager_state
    systemctl start kubelet          # we stopped it, we restart it
  else
    rm -f /var/lib/kubelet/cpu_manager_state /var/lib/kubelet/memory_manager_state
  fi                                # normal boot path: Before=kubelet.service ordered us first,
                                    # kubelet is not yet up — the boot transaction starts it after us
}
exit 0                              # a hook failure must never block boot

Properties: ordered Before=kubelet.service; the interface-manager wait is two-condition gated (manager script present + Mellanox vendor 15b3 in sysfs — the sysfs-native equivalent of the bash lspci -d 15b3:* check, no pciutils dependency), because the manager's unit only exists when the hardware does and an unconditional wait can never succeed on a node without it; the kubelet-state reset is guarded the way fn_ensure_state does it — stop kubelet if it is running, delete, restart — because deleting the files under a live kubelet races its re-persist of in-memory manager state and the stale file survives (in the normal boot path kubelet is not yet up, so this reduces to a plain rm); every action best-effort (the hook always exits 0 — a hook failure must never block boot, it degrades to today's failure mode at worst); content-hashed, so the agent re-renders it on profile change and detects out-of-band edits; installed under the node lease at adoption, disabled on de-adoption. Adoption deletes the rc.local entry — this unit is the only OS boot integration the controller ever installs. Profile knobs: hostBoot.kubeletStateReset: always | readyCheck | off and hostBoot.mlnxInterfaceMgr: wait (default: hardware-gated wait, then netplan apply) | disable (mask the service outright — opt-in after validating nothing else on the distro depends on it; the wipe bug itself is upstream in mft) | ignore. The gate predicate is one shared, unit-tested function used by the hook (rendered as shell), the agent's coexistence wait (§9.2), and the agent's decision of whether the manager is even in scope.

6.3CAPI integration: absorbing the legacy controller

The existing nodeprep-controller Deployment fixes P13 watches Nodes and performs three duties keyed off bash label strings. All three move into the new controller, driven by NodePrep phases instead of label values:

Legacy behaviorTrigger todayIn the new controller
Remove spectrocloud.com/nodeprep:NoSchedule when the label reads completelabel == completeSuperseded by the taint contract (§6.1): released by agent boot-verify, never by a label value

The CAPI pause deserves its rationale in writing: reboots during nodeprep otherwise look like node failures to MachineHealthCheck, which can respond by deleting and recreating the Machine mid-flash — the worst possible intervention. Pausing the Machine (not the MachineDeployment, matching today's granularity) suppresses exactly that while nodeprep owns the node. On Failed, the Machine stays paused: remediation-by-recreation of a half-flashed node is worse than a loud object, and the same explicit recovery that restarts nodeprep (profile bump or resume annotation) unpauses it. Worker-role label timing is unchanged in spirit: the node is demoted from worker pools before the disruptive finalization begins and promoted only after verification.

6.4Control-plane choreography

Prepping control-plane nodes is a quorum problem, and the bash script solved it with a 30-minute blind sleep fixes P9. The controller replaces the sleep with a gate and an admission policy. The same machinery then makes rolling control-plane upgrades a natural extension rather than a new problem.

  • Expected CP count first. The controller reads the expected control-plane replica count from the cluster's KubeadmControlPlane.spec.replicas (CAPI is present on every Palette-managed cluster); controlPlane.expectedCount overrides for non-CAPI clusters. Typically 1 or 3.
  • Bootstrap gate for fresh clusters. A control-plane node is tainted and prepped only after the CAPI ControlPlaneInitialized condition and cert-manager Availability — real signals for what sleep $CP_DELAY was approximating. While the gate is open, CP nodes are untainted so cluster initialization (add-ons on a fresh single-node cluster) proceeds normally. If neither signal is reachable, the gate falls back to controlPlane.bootstrapDelay — a named, tunable, observable wait instead of a blind one.
  • Quorum admission. The controller admits at most expectedCount − quorum(expectedCount) CP nodes into prep concurrently — 1 for a 3-node CP, 2 for a 5-node — and schedules them serially. A 3-node control plane is never more than one member short of quorum: while CP-1 reboots, CP-2 and CP-3 serve etcd and the API. Add-on pods that landed on CP-1 during the untainted window reschedule onto the still-untainted members as each wave runs. MaintenanceAdmitted carries the reason while a node waits its turn.
  • Single-CP clusters: background mode. The quorum math allows zero disruptions, but the work must still happen — so nodeprep runs in the background against the live node, and the reboots are an unavoidable, announced disruption (Events, cordon per policy). The taint contract still governs workload placement; what it cannot protect is the API server sharing the node's fate across its reboots. Documented trade-off, not a hidden one.
  • Worker nodes prep concurrently with all of the above — no quorum constraint — bounded only by the fleet flash window (§9.1).

Triggers, not modes

Stylus and /etc/rc.local were never two behaviors of the script — they are two triggers for the same script. Stylus invokes it on Stylus-managed clusters; rc.local does it on CAPI clusters, where Stylus is absent. The new design replaces both triggers with the DaemonSet on every cluster type, so nothing needs to invoke nodeprep from the OS anymore. During migration, a node where the Stylus trigger is still active stays in bash mode until its adoption wave — the two implementations never run concurrently on one host.

VF management is not delegated

The SRIOV / NVIDIA network-operators are deliberately not given ownership of VF creation, GUIDs or renaming. Spectrum-X 2.1 requires the VFs to be managed externally to the Network Operator — that is, by this controller — and the GUID scheme and rename grammar are fabric-load-bearing. fn_set_vfs is re-implemented here in full, not approximated by a delegating integration.

The subtlest part of the bash script, preserved exactly — with the classification made explicit and testable.

8.1Device classification

For each Mellanox PCI function found via mst status -v, the agent queries mlxconfig q INTERNAL_CPU_OFFLOAD_ENGINE. The presence of a Description: line distinguishes physical engines from the N/A case, and the Device type: string classifies:

Multi-plane detection (the v105 addition) is kept: when more than one mst entry resolves to the same PCI function, the rail label gains a plane suffix (r0_p0, r0_p1), and netdev selection excludes entries whose phys_port_name matches vf — identical to the awk/sed chain, but as a tested function over sysfs.

8.2Rail assignment

v1 keeps the bash semantics as the default: spec.rails is an explicit, ordered PCI-function → rail map (the rails_pciaddr env var, made declarative and validated at admission — unknown functions produce an Event, not silence). An opt-in railSource: lldp can derive rails from switch port descriptions — lldpd is already installed and configured by this very controller — but ships off by default: switch-side description conventions are not assumable to be stable across the switch vendors in the fleet, and a misparsed rail silently rewires the fabric. It stays an open validation question (§11), not a default.

8.3VF GUID scheme — reproduced verbatim

The GUID/MAC derivation is load-bearing for the fabric (roce_vf names and GUIDs are what the spectrum switches and fabric managers expect), so the controller reproduces the v105 arithmetic byte-for-byte. From the PF's node_guid (hex, colons stripped, 16 chars), for VF index v in two-digit hex:

AttributeDerivationWritten to
VF node GUIDraw[0:7] + "f1" + v₂ + raw[11:16]/sys/class/infiniband/<ib>/device/sriov/<vf>/node
VF port GUIDraw[0:7] + "f2" + v₂ + raw[11:16] (IB link type only)…/sriov/<vf>/port
VF MAC"f2" + v₂ + raw[8:16] (ETH, legacy eswitch only)…/sriov/<vf>/mac
Policy"Follow" (IB only, non-critical on failure)…/sriov/<vf>/policy

After writing, the VF's PCI address (from virtfn<v>/uevent) is unbound and rebound on mlx5_core to activate the GUIDs, then read back for verification — the exact sequence of fn_set_vfs, as three small functions with unit tests over fixture GUIDs. The VF and representor udev rules (nic_vfN_rM, roce_vfN_rM + cma_roce_tos -t 96, nic_vfN_rep_rM keyed on phys_switch_id/phys_port_name) are emitted from the same data that produced the GUIDs, so rules and GUIDs can never disagree.

8.4GPU inventory

NVIDIA 3D controllers are enumerated by PCI class 0x03 / vendor 0x10de straight from sysfs (no lspci fork), capturing name, current link width and max link speed into status.gpus[] — the same data the bash script labeled, minus the subshell counter bug.

Safety & policy

The gates the bash script enforced, plus the ones it couldn't.

9.1Hardware safety

  • policy.controlDPU: false short-circuits every DPU step — flash, mlxconfig, offload-engine — each reporting condition reason SkippedByPolicy. Identical to CONTROLDPU, but auditable from the object instead of a log line.
  • Version-gated flashing: flash only when flint q firmware sorts below firmware.bfb.min (same ordering rules as vercomp, including its zero-padding behavior).
  • Fleet flash window: the controller admits at most maxConcurrentFlashes (count or percentage) NodePreps into Flashing at once via the FlashAdmitted condition; the agent blocks before the flash step until admitted. A rack powers up and flashes in waves, not all at once (fixes P7).
  • Integrity everywhere: sha256-pinned downloads, atomic tmp+rename (kept from bash), read-back verification on every sysfs/mlxconfig mutation, ACS read-back, GUID read-back (fixes P4).
  • ACS: disabled per policy across all PCI functions with the same skip-if-unsupported logic; re-checked on resync since BIOS updates can re-enable it.

9.2Workload safety

  • Cordon windows: node cordoned for eswitch/VF mutations through device-plugin resync (the bash fn_set_vfs…fn_restart_sriov_devplugin span), and optionally across reboots. Cordons are controller-owned records so an agent crash can never leave a node cordoned — the controller reconciles cordon state from NodePrep conditions. For CAPI clusters, the Machine pause (§6.3) covers the same span.
  • Disruptive steps declare themselves. During bring-up they run under the held taint; on a Ready node they only run after the controller re-applies the taint — the maintenance-window re-entry of §6.1 — or, for non-disruptive drift, in place (§5.3).
  • Taint lifecycle: applied at adoption (control-plane nodes: only after the bootstrap gate, §6.4), released only by boot-verify (§6.1), re-applied for maintenance. The fresh-control-plane dance from fn_ensure_state (untaint so cert-manager can schedule on a single-node cluster, wait for its helm secret, retaint) becomes the controller's bootstrap gate plus quorum admission (§6.4), replacing a bare sleep $CP_DELAY with named, tunable, observable waits (fixes P9).
  • Credentials: BMC credentials live in a Secret referenced by the profile; rendered into bf.cfg only for the duration of the flash, never logged, and the new-password length rule (≥12 chars, else skipped with a warning Event) is enforced in code (fixes P5).
  • Interface-manager coexistence: if the manager script is installed and Mellanox hardware (vendor 15b3) is enumerated, the agent waits for its slice to settle exactly as bash does — the same two-condition gate as the boot hook (§6.2), since the unit only exists when the hardware does — then owns the interfaces. Either condition false ⇒ no wait, no scope. Both writers active simultaneously is a deployment error; the lease makes the second writer visible.

9.3Failure semantics

Every failure path terminates in one of three states: a retry with backoff (transient: downloads, apt, flash), a reboot (the kernel/hardware demands it), or Failed (budget exhausted). Failed is loud — Event, metric, condition with step name and output tail — and cheap to recover from: fix the cause, bump the profile, and only the affected steps re-open. Nothing is ever silently retried forever again.

9.1Rollout sequence

  1. Shadow mode. Deploy the agent with --mode=shadow on nodes already prepped by bash: every step runs Detect only, and its verdict is recorded. A correctly modeled step reports Done on every bash-converged host; any Drifted verdict is a modeling bug to fix before the controller can apply anything. Shadow mode turns the migration risk into a checklist.
  2. Import. The converter reads nodeprep.env into a NodePrepProfile; the controller maps the legacy label to a phase (init→Provisioning, inithw→Flashing, config→Configuring, precomplete/complete→Finalizing). Because every step verifies before declaring Done, a mis-mapped import self-corrects on first Detect. In the same step the new controller deploys and the legacy nodeprep-controller Deployment is removed — its untaint, CAPI-pause and worker-label duties are now native (§6.3), and running both would fight over taints.
  3. Canary. A labeled canary set gets rc.local removed and full controller ownership; fleet flash window set to 1. Watch step metrics and reboot counts across two full reboots.
  4. Fleet. Remaining nodes adopt in waves; labelCompat: v1 keeps existing dashboards green throughout. The bash scripts stay in the repo untouched until the last node is imported, then move to attic/.

9.2Testing strategy

  • Pure logic (GUID scheme, classification parsing, semver compare, grub assembly, profile defaults) is unit-tested against fixtures captured from real nodes — including the mst/mlxconfig output quirks the awk chains were tuned around.
  • Host boundary is an interface (type Host interface in internal/host) with a scripted fake, so the entire stage engine runs in CI without hardware.
  • envtest covers controller behavior: adoption, flash-window admission, taint lifecycle, bootstrap gate, CP quorum admission, CAPI pause, worker-label transitions.
  • Hardware-in-the-loop: one lab node runs the agent against a nightly converge → wipe → reconverge loop — the closest thing to what the bash script could never give us: a regression test for the whole bring-up path.

Open questions

Decisions deliberately left open, with the information needed to close them. Resolved by review: VF management stays in-house (Spectrum-X 2.1 requires VFs managed externally to the Network Operator — §7 note); Ready-state converge uses the middle ground — non-disruptive repair in place, disruptive repair behind the taint window (§5.3, §6.1); post-reboot workload protection is solved by the taint contract (§6.1); CAPI pause, worker-role label and untaint are absorbed from the legacy controller (§6.3).

  1. LLDP rail discovery — a validation task, not a design task. railSource: lldp ships as an opt-in mechanism with the explicit spec.rails map as the default, because switch-side port-description conventions are not assumable to be stable across vendors. Closing this means auditing the actual port descriptions per switch vendor in the fleet and defining a parsing contract per vendor.
  2. mlnx_interface_mgr: repair vs. remove. The boot hook defaults to wait-then-netplan apply (parity with the bash script). mlnxInterfaceMgr: disable (mask the service) exists but needs a validation pass per affected distro image to confirm nothing else consumes the manager. The wipe bug itself is upstream in mft and should be tracked there; the boot hook is the workaround, not the cure.
  3. kubeletStateReset: readyCheck. Skipping the pre-kubelet state-file deletion when NodePrep is Ready would preserve CPU-manager pin assignments across ordinary reboots. It stays opt-in until validated against the target kubelet version's state-restore behavior — a wrong guess deadlocks the node (kubelet won't start, agent can't run). The fail-safe default remains always.
  4. Stylus as a profile consumer. On Stylus-managed clusters, whether Stylus should create NodePrepProfiles per cluster template (rather than the DaemonSet adopting nodes by selector) is a product decision, not an engineering one. Engineering's position: the API is already shaped for it.
  5. Control planes without CAPI. CP choreography needs an expected replica count; on clusters without CAPI it must come from the profile. Decide whether that is a documented requirement or whether Palette guarantees CAPI everywhere nodeprep runs.
